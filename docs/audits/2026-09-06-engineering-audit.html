A system whose invariants are engineered better than its modules. Everything the constitution names is enforced by a test or an AST guard. Everything it does not name (function size, helper duplication, prompt-schema drift, sandbox flags) has drifted, because nothing measures it.

The one-paragraph verdict

Devclaw is unusually honest about failure: fail direction is declared at every parse site, the zero-token idle guard is a real test, single-writer is structurally true, and config has exactly one doorway. That is rarer than it sounds and it is the reason the loop runs unattended at all. The debt is elsewhere. Four modules of 1.5k to 2k lines hide 700-line and 400-line functions with 16 to 22 keyword parameters; the same helper (git wrapper, JSON extractor, clock) is written 5 to 9 times; source comments carry 270 issue references and docs are two-thirds frozen history; the most important prompt is half markdown and half Python literals whose schema disagrees with the parser; and the expensive path, the worker, is the one whose prompt and token usage the system cannot show you afterwards. None of this is tangled enough to trap a refactor. All of it is the kind that accumulates silently, which is why the second half of this page proposes a recurring measurement rather than a one-off cleanup.

A recurring review: the eng-health skill

Every finding above has the same shape: an invariant the constitution does not name, drifting because nothing measures it. The named invariants did not drift, because a test or an AST guard holds them. So the recurring review should not be "re-read 47k lines with an LLM every month". It should be a ratchet, in the same shape as the scorecard, whose job is to turn judgment findings into mechanical guards until the review itself is small.

Design rule. The skill measures mechanically, judges only what moved, and disposes of every finding into exactly one of four bins. Its success metric is how many of its own metrics have graduated into tripwire tests. A review that reports the same finding twice has failed.

Shape

1 · measure

A zero-LLM script, evals/measure_eng_health.py, prints one JSON blob of metrics. Runs in seconds, runs in CI as informational.

  • Structure: functions over 80 and over 200 lines; modules over 1,000 lines; parameter counts over 8; cross-package imports of underscore names; imports that violate a declared layer allow-graph; os.environ reads outside the doorway.
  • Duplication: AST-normalised function-body hashes shared across modules; vulture at 80%; broad excepts with no raise, log or trace in the handler.
  • Noise: issue-reference density per module; "formerly / used to / legacy" phrase count; spec headers whose status disagrees with their tasks checkboxes and merged PRs; INDEX rows over 1,500 chars; CLAUDE.md line count.
  • Prompts: estimated tokens per template including Python-appended literals; schema keys in the markdown versus keys the parser reads; templates lacking the grounding clause; parse sites lacking a declared fail direction; eval fixtures per prompt.
  • Harness: docker flags versus a hardening allowlist; worker tasks with recorded usage as a share of all; brief size distribution from recent traces; brake table extracted from config.
2 · delta

Compare against the previous run, read from git history of the keep-latest report. Report only metrics that regressed, crossed a threshold, or are new. Absolute numbers stay in the table; the narrative is the delta.

3 · judge

One deep read per run, rotating through four lenses: layering, duplication and noise, prompts, harness and context. Each lens has a fixed question list, the ones this audit used. A full deep read happens every four runs; each run costs one lens plus the deltas. The judge is told the mechanical numbers first so it argues from evidence, not impression.

4 · dispose

Every finding leaves in exactly one bin, recorded in the report:

  • fix now: mechanical, tinyspec-sized, done in the same session. Never becomes an issue.
  • promote to guard: write the tripwire test that makes the metric unable to regress, then drop the metric from the script. This is the bin the skill exists for.
  • spec: a class-level design change. Opens /speckit-specify with the finding as the problem statement.
  • accept: carries an owner and a regrade date on the same line, per the vault's clock rule. A bare accept is refused.
5 · capture

Overwrite docs/audits/eng-health.md (keep-latest, git is the archive) with the metrics table, the deltas, the findings and their bins. One dated line in the vault log. No session exhaust anywhere else.

Trigger

Not a calendar. The trigger is mechanical and surfaced where Denys already looks: /morning-status prints "eng-health due" when merged PRs since the last report exceed 15, or when any spec header flips to Implemented. The weekly Monday release is the natural backstop. The skill is invoked by Denys, never by cron, because phase 4 needs a human on the spec and accept bins.

Why this and not a plain review skill

A plain review skill re-reads the tree and re-discovers the same nine git wrappers next month. It scales with the codebase and its findings scale with the model's mood that day. The ratchet shape scales with what changed, its numbers are comparable across runs, and every finding it promotes to a guard is a finding it never has to make again. That is also the only version that fits the repo's own doctrine: the suite is a tripwire net, and this is the machine that grows the net from evidence instead of diligence.
